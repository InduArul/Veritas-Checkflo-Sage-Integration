5) CLIENT QUESTION INVESTIGATED (Empres) - Bill 35505383
   Q: "Why was bill 35505383 not assigned to Firesteel?"
   Facts: Vendor V00069 "Direct Supply", $106.20. Intacct GL line Location =
   "170--Firesteel Healthcare Center". Bill CREATED AT TOP LEVEL (header has no
   entity). Output file showed Facility = "TOPLEVEL", Entity = "TOPLEVEL TOPLEVEL".

   HOW v9.0 ASSIGNS FACILITY:
     - Default: from MEGAENTITYNAME (entity the bill was CREATED AT).
       Module 408 (query APBILL header) -> 410. Top-level bills return blank
       -> renders "TOPLEVEL". No location read here.
     - Fallback for blank/top-level rows: router 417 "When Location is Empty or EVG"
       -> module 438 queries APBILLITEM (LINE items) for LOCATIONNAME, matched by
       RECORDID IN (...) -> 452 parse -> 445/446 Power Automate "top level location
       update" writes it to Bills tab -> 458/461 + 453/377 map LOCATIONNAME to a
       facility via FacilityMapping.json (Excel Location/Mapping worksheet).

   ROOT CAUSE (read-only analysis; design DOES read line location, so my first
   "header-only" guess was WRONG):
     The bill was created at TOP LEVEL, so it depends on the fragile fallback,
     which failed to resolve Firesteel. Two break points:
       (1) Module 438 matches purely on RECORDID (bill DOCUMENT number, not the
           unique RECORDNO). Document numbers can collide across entities/years and
           multi-line bills return multiple locations -> wrong/empty match. Saved
           sample shows 35505383 -> "Conestoga View SNF Operations LLC" (NOT
           Firesteel) [caveat: that sample is from an Evergreen run].
       (2) Returned location may not exist in FacilityMapping (Location/Mapping
           worksheet), so it can't translate -> cell stays "TOPLEVEL".
     Output literally "TOPLEVEL" => overwrite never landed for this row.
   UPSTREAM CAUSE to flag to client: bill was ENTERED at Top Level in Intacct
   instead of under the Firesteel entity.

   RECOMMENDED FIXES (not yet applied):
     - Quick: add Firesteel location row to the Location->Mapping worksheet.
     - Robust: change module 438 match key from RECORDID -> RECORDNO (unique),
       and handle multi-line bills deterministically.

   TO CONFIRM DEFINITIVELY (still pending):
     - Get latest Empres_toplevelrecords.json + Empres_FacilityMapping.json from
       SharePoint (.../CheckFlo API/Check files/Support files), and/or
     - Check whether Location->Mapping worksheet has a "Firesteel" / "170" row.

6) UPLOAD CSV TO CHECKFLO v0.1 (id 4492713) - 503 "failed fetching location name"
   Run 2026-06-18 11:43 AM ET = 15:43:17Z (execution e38d6bf...; status 1/OK).
   ERROR observed in UI: type ConnectionError, "[503] We're sorry...". This is a
   transient Microsoft Graph/SharePoint 503 (Server Too Busy) on module 177
   (microsoft-excel:listTableRows of Bank_Table), called ONCE PER GROUP inside the
   groupBy-aggregator loop (module 70, groupBy {{8.col1}}).

   CORRECTED ROOT CAUSE (my earlier "it retried and recovered" was WRONG):
   - Module 177 has NO retry on itself. Its onerror chain = [241 GetVar read counter,
     242 addATableRow "Error reading the Mapping file", 244 makeApiCall rename file to
     "_failed.csv", 243 SetVar increment No_of_files_process_failed]. The only Break
     retry (266, retry 3x/1min) is nested as the onerror of 244 (the RENAME step), not
     the lookup.
   - So a 503 on the lookup is NOT retried; it is logged as a FAILED file (counter++,
     file renamed _failed.csv). The throttle also typically OUTLASTS short retries
     (Graph/SharePoint throttle windows can be minutes; retrying w/o honoring
     Retry-After can EXTEND them).
   - Net: transient Microsoft blips were being mis-reported as failed files.

   THE FIX (built, QA-passed; NOT pushed) - "fetch Bank_Table once":
     scratch/build_fix_uploadcsv.py -> scratch/UploadCSV_to_Checkflo_v0.1.FIXED.blueprint.json
   - ROOT flow, after module 175 (runs once):
       [313] microsoft-excel:listTableRows Bank_Table (all rows; onerror Break retry
             5x/2min) -> [314] builtin:BasicAggregator (Array Aggregator, feeder=313,
             no Group By, element {values:{...}} preserves shape) -> [315]
             util:SetVariables scope=execution Bank_Table_all = {{314.array}}.
   - IN-LOOP: [177] retyped microsoft-excel:listTableRows -> builtin:Iterator over
       {{315.Bank_Table_all}} (keeps TOPLEVEL/petty-cash filter; onerror 241-244 dropped).
   - 179 (feeder 177) + 295 unchanged; {{177.values.`4`/`5`}} still resolve.
   - Result: Bank_Table Graph calls N -> 1; no 503; records no longer false-failed.

   D3 (report dependency) RESOLVED - SAFE to drop 241-244:
   - Counters No_of_files_process_successful / _failed / _partial_failed are init in
     module 118 (=0), incremented in ~7 OTHER handlers (235,228,119,186,75,127,...),
     and READ for the downstream report (module 75 etc.; filter checks failed!=0).
   - 241-244 fired ONLY on the Excel API error (503), which the in-memory fix
